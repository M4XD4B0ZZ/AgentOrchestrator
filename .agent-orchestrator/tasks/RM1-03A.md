## 1. The one hard requirement

When the writing agent fails, its **original failure code** survives the step on disk, beside the
task record, as **evidence only**. Today it is lost: `recordInterruption`
(`src/loop/loop-step.ts`) receives a `ClaudeWriterFailed` with `code`, but passes only `disposition`
and `block` to `recordAgentInterruption`. Eight codes map to `AGENT_NEEDS_ATTENTION` and leave a
byte-identical task record, so `AGENT_ARGUMENT_REFUSED` (deterministic) cannot be told from
`AGENT_PROCESS_UNAVAILABLE` (transient).

## 2. Invariants (each one is tested)

1. **Task-state semantics do not change.** `TaskState`, its schema, `core/transitions.ts`, every
   state a step writes, and every byte of the task's state file stay as they are. Test: the state
   file is byte-equal with the evidence write and without it (a seam that refuses the write).
2. **Evidence never decides.** Only `src/loop/loop-step.ts` (write) and `src/run/run-plan.ts`
   (display, section 3.4) import the new store. Tests: an import pin over `src/`; and the plan's
   selection, target, state, conclusion and reasons are equal with the record present, absent and
   unreadable — only the display line differs.
3. **Bounded.** At most `MAX_WRITER_OUTCOMES_KEPT = 8` entries per task. A ninth entry drops the
   oldest and adds 1 to `droppedCount`, so a loss is visible. The file has a byte cap like its
   sibling stores.
4. **Closed values only (redaction by construction).** No stdout, no stderr, no excerpt, no
   `AgentDiagnostics`, no CLI text, no path of the operator's home. The schema is `.strict()`; a
   field outside section 3.2 fails the read-back.
5. **Atomic and robust.** The write follows `src/verify/verification-attempt-store.ts` step by step:
   derive the location (task id checked with `isValidTaskId`, path contained in the repository), read
   what is there first, `git check-ignore` for the record and its staging name, binding digest,
   read-back before the write, byte cap, `mkdir`, the lease check last, `writeFileAtomically`,
   read-back after. An unreadable existing record is never overwritten (`EXISTING_HISTORY_UNREADABLE`).
6. **A failed evidence write changes nothing else.** It never changes the step's outcome, the state,
   the exit code, or what any later step does. It is reported, never thrown.
7. **MEMGUARD stays intact.** Nothing here touches `src/agent/writer-write-guard.ts` or the guard's
   evidence; the writer's write guard still wraps every launch.

## 3. What to build

### 3.1 Files

- New `src/agent/writer-outcome.ts`: the record schema, version, binding and the pure reader, like
  `src/verify/verification-attempt.ts`.
- New `src/agent/writer-outcome-store.ts`: location, record (append), load, like
  `src/verify/verification-attempt-store.ts`. Directory `writer-outcomes` under
  `taskRuntimeDirectory(repositoryRoot)` (`src/state/state-location.ts`); file `<taskId>.json`.
- `src/loop/loop-step.ts`: `recordInterruption` and the result shape only.
- `src/run/run-plan.ts` and `src/run/render-run-plan.ts`: the display line of section 3.4 only.
- Tests: new `tests/rm1-03a-writer-outcome-evidence.test.ts`; existing tests only for a new field.

### 3.2 One entry

`{ recordedAt, phase: 'IMPLEMENT' | 'REMEDIATE', round, code, disposition, detail, process,
forbiddenWriteRecorded }`:

- `code`: the `AgentFailureCode`, unchanged.
- `disposition`: the `AgentDisposition` it mapped to.
- `detail`: `AGENT_FAILURE_TEXT[code]`, the static sentence (the cause in words; never CLI text).
- `process`: the closed fields of `AgentProcessEvidence` (`outcome`, `exitCode`, `signal`,
  `outputTruncated`, `failureCode`, `errnoCode`, `durationMs`).
- `forbiddenWriteRecorded`: `true` only when the writer result carries a forbidden-write evidence
  record with a non-null path; else `false`. Never the path.

The document: `{ outcomeVersion: 1, taskId, repositoryRoot, droppedCount, outcomes, binding }`.

### 3.3 The write

In `recordInterruption`, on **every** path out of it (the scope-gate return, `STATE_NOT_RECORDED`
and `BLOCKED`), after the state write was attempted: append one entry. Use the lease and the Git
runner the step already holds. Add `writerOutcomeEvidence: { recorded, code, path } | null` to
`LoopStepResult` (default `null` in `result()`), filled only here. No other step writes it.

### 3.4 The read

Export one loader. `run-plan.ts` loads it into one display field; `render-run-plan.ts` prints one
line: `Writer outcome: <code> (<phase> r<round>, <recordedAt>)` for the newest entry, `none` with no
record, `unreadable` for any other reading. It decides nothing.

## 4. Tests — red first

In `tests/rm1-03a-writer-outcome-evidence.test.ts`:

1. **One case per failure class** that reaches `recordInterruption` from the writer: process
   (`AGENT_PROCESS_UNAVAILABLE`, `AGENT_NONZERO_EXIT`, `AGENT_ARGUMENT_REFUSED`), result
   (`AGENT_RESULT_MALFORMED`), write guard (`AGENT_FORBIDDEN_WRITE`, `AGENT_WRITE_QUARANTINED`,
   `AGENT_WRITE_GUARD_UNAVAILABLE`), quota (`AGENT_USAGE_LIMIT`), auth (`AGENT_SESSION_REJECTED`).
   Each keeps its exact code, disposition and static detail; IMPLEMENT and REMEDIATE both.
2. Invariant 1: the state file is byte-equal with and without the evidence write.
3. Invariant 3: nine failures keep the newest eight, `droppedCount` 1, under the byte cap.
4. Invariant 4: a writer result whose diagnostics hold text (for example a token-shaped string)
   leaves no byte of it in the record; an extra field fails the read.
5. Invariants 5 and 6: a path that is not ignored, a lost lease, a write error and an unreadable
   existing record each leave the step outcome and the state unchanged, report a closed code, and
   never overwrite the unreadable file.
6. The runtime readers still see only task records: the dashboard scan, the attention outbox and the
   durable wake list no task named `writer-outcomes`.
7. Invariant 2: the import pin, and the plan equal with the record present, absent, unreadable.
8. The display line: newest entry, `none`, `unreadable`.

Each case must fail on a copy with the part it pins removed.
