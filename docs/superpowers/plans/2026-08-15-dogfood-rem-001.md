# DOGFOOD-REM-001 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the four rerun-blocking product defects the first real attended dogfood (`CARGO-UI-001-DOGFOOD-20260815-01`) exposed, so that a second dogfood can deliver the proof the first one could not: real code transported across the controlled commit chain.

**Architecture:** One authority split and three information-flow repairs, none of which adds a durable field.

The **authority split** is the centre. Claude becomes an *editor* — hermetically configured, cwd-confined, with no shell, no git and no MCP — and the orchestrator becomes the **commit owner**: it measures what the writer actually did, enforces scope on it, creates the task commit under its own lease, and re-measures HEAD and cleanliness before `VERIFYING` may follow. A writer phase with no measured effect is no longer a success, and the structured `permission_denials` the CLI already prints is read and reported instead of discarded.

The three repairs each remove a way for a truth to go missing. **Settlement** gains the one conjunct it lacked, so `READY_FOR_PR` cannot be reached with an empty task delta, checked against freshly observed evidence. **Chain fitness** gains a ledger-local refusal, so a predecessor whose result is the tree it started on can never prove delivery to a successor — which is what defuses the tautological records the dogfood already wrote to disk. The **reviewer** receives the task's own words instead of only its id, and the **remediation hand-off** stops falling through the step-budget boundary.

No new ledger field. No new stop reason. No task-state schema change. One new member of a report-only refusal set.

**Tech Stack:** TypeScript 7 (ESM, `nodenext`), Zod 4, Commander 15, vitest 4, GitHub Actions on `windows-latest`, Node 22 and 24.

**Design:** The DOGFOOD-REM-001 design read of 2026-08-15 and the decision reply of the same day (Decision 1 = Variant A, Decision 2 = no schema change). The design read and that reply *are* the spec; their content is reproduced in the Global Constraints below rather than referenced, so this plan is self-contained.

**Provenance of line numbers:** every citation below was taken at `main` = `71b717f`. Re-confirm before editing; a citation that has drifted is a signal to re-read, not to guess.

## Global Constraints

Every task's requirements implicitly include this section. G1 and G2 are the settled decisions and outrank anything a task says.

### G1 — Decision 1: the orchestrator owns the commit

```text
Claude
  → may read and edit inside the task worktree
  → may NOT run git, a shell, or an MCP tool
  → delivers filesystem changes and nothing else

AgentOrchestrator
  → measures the real effect of the writer pass
  → enforces scope on it
  → creates the task commit under its own lease
  → re-measures HEAD and cleanliness afterwards
  → only then may VERIFYING follow
```

The commit happens **after** the scope check, never before. We must not commit a change that lies outside the allowed scope and discover afterwards that it was forbidden.

**Consequence that must not be missed: `writerThatCommits` is now wrong and must be retired.** Under G1 a committing writer models a capability production forbids. It is replaced by `writerThatEdits`, and a control asserts the writer has no git authority at all. Any plan step that reads "switch the fixture to `writerThatCommits`" is superseded by this constraint.

### G2 — Decision 2: no empty-delta rule in the task-state schema

The storage schema stays structural and backward-readable. The dogfood record

```text
READY_FOR_PR
currentCommit == basePinnedCommit
```

was syntactically valid under the schema in force when it was written. Reclassifying it after the fact as `STATE_UNUSABLE` would be a misdescription: it is neither broken nor somebody else's, it is a false completion that an earlier product defect authorised. So two separate layers, and no third:

```text
future transitions      READY_FOR_PR only when currentCommit != basePinnedCommit,
                        against freshly observed runtime evidence

old / foreign records   SETTLED predecessor whose resultCommit == its own baseCommit
                        → CHAIN_* refusal → the successor does not start
```

No ledger field, no stop reason, no schema bump, and **no change to `src/core/task-state.ts`'s `READY_FOR_PR` block.**

### G3 — The measured writer vector, bound to CLI 2.1.233

`CLAUDE_WRITER_ARGS` becomes exactly:

```text
--print
--output-format json
--setting-sources ""
--strict-mcp-config
--permission-mode acceptEdits
--tools Read Edit Write Glob Grep
```

Every token is shell-inert under `SAFE_ARG_PATTERN` (`src/doctor/exec.ts:93`), including the empty string, whose pattern is `*`-quantified. Each element is justified by a measurement, not by recollection — see the evidence table in G4. **Do not substitute a remembered flag for a measured one.** In particular:

- **`--bare` is refused.** The installed CLI's own help states its auth is *"strictly `ANTHROPIC_API_KEY` or `apiKeyHelper` via `--settings` (OAuth and keychain are never read)"*. AO runs on the subscription login that `auth:claude` preflights, so `--bare` would break authentication. This is read from the installed binary, not assumed.
- **`--safe-mode` is refused as the hermeticity mechanism.** Measured: it suppressed user-scope configuration but the *project* `CLAUDE.md` still took effect, contradicting its own help text, which lists `CLAUDE.md` among what it disables. A flag whose documented and measured behaviour disagree is not a boundary we build on.
- **`--strict-mcp-config` is load-bearing and non-obvious.** `--tools` does **not** bound MCP authority. Measured: with `--tools Read Edit Write Glob Grep` and no `--strict-mcp-config`, the writer held the operator's MCP tools and attempted one — `permission_denials: ["mcp__claude_ai_Gmail__list_labels"]`. With it, the tool set is exactly `Edit, Glob, Grep, Read, Write` and MCP is absent.
- **No settings file carrying authorisation rules.** Rule-scoped permissions are only expressible through a settings file, and the measured behaviour of that route is treacherous: an *unqualified* `Write`/`Edit` allow-rule grants unbounded write authority — the writer escaped the worktree and overwrote a tracked file in the sibling main checkout — while `Write(**)`/`Edit(**)` happens to restore containment. That semantics does not belong in a security-critical product boundary when it can be avoided. `--permission-mode acceptEdits` is cwd-confined on its own, measured, with both escapes blocked.

**Hermeticity has a cost that must be paid deliberately.** `--setting-sources ""` suppresses the target repository's own `CLAUDE.md`, so repository conventions no longer reach the writer ambiently. That is the point — the operator's machine must not decide the writer's behaviour — but the conventions are often genuinely useful. Where a repository wants them, AO passes the `CLAUDE.md` **path** through the payload's existing `CONTEXT SOURCES` section, which the writer can `Read`. The channel becomes explicit and AO-controlled instead of ambient. Paths only, never contents — the existing rule.

### G5 — The separate path/sandbox anomaly is closed as the same defect, with one residual check

The dogfood reported a sandbox/path refusal for a path that appeared to be inside the declared task worktree. Three candidate mechanisms were probed and **all three were falsified** — writes succeed in a plain clone, in a linked git worktree whose `.git` is a file pointing outside cwd (the production shape), and in a worktree reached through an NTFS junction.

The positive explanation, with evidence: the CLI narrates permission denials in path language. Observed strings include *"outside my allowed folder"* and *"This path is outside the working folder"* — including in a case whose true cause was an unmatched permission rule. With no permission mode, every write is denied and the agent is free to attribute that to the folder.

**Residual, and it is a rerun-gate item, not an assumption:** compare the dogfood transcript's literal refusal strings against those observed strings. Match → closed as the same defect. No match → a live second mechanism, and the rerun blocks again.

### G6 — `permission_denials` is reported, never a verdict on its own

```text
structured permission_denials   never ignored, always reported
no measured task delta          writer success inadmissible
delta present                   scope + AO commit + verify + review decide onward
```

A writer may attempt a forbidden access it did not need and still deliver a complete implementation inside its authority. So a non-empty `permission_denials` does **not** by itself fail the pass. What fails the pass is the *absence of a measured effect*.

**"Reported" names a surface, and the surface is asserted.** Parsing the field
and carrying it on an in-memory outcome is not reporting; it is being in a
position to report. The dogfood's failure mode survives a product that only
parses:

```text
operator sees   "Run BLOCKED / State HUMAN_DECISION_REQUIRED / no measured effect"
never sees      "the writer reported 2 denied tool uses: Write, Bash"
```

— which is the same diagnosis loss, one layer further in.

It is reported on **every** writer pass that produced denials, including passes
that then succeed — a denial on a run that completed is exactly the signal that
the authority vector is one flag away from being wrong, and it is worthless if
it is only printed on failures. **That requirement decides the carrier**, and it
rules out the obvious one:

```text
IMPLEMENT   denials=[Bash]   → ADVANCED
VERIFY                       → ADVANCED
REVIEW                       → stop

RunResult.lastStep = the REVIEW step        ← the writer's observation is gone
```

A per-step field reaches the renderer only when the run happens to stop on the
writer step — precisely *not* the successful case this rule exists for. So the
carrier is **run-level and accumulating**:

```text
ClaudeEnvelopeReading
  → writer outcome
  → the run driver accumulates every writer pass's observation, in order
  → RunResult
  → renderRunResult  (src/cli/render-attended-run.ts:130)
```

Aggregation, not last-writer-wins: a run whose round 1 was denied `Bash` and
whose round 2 was clean must still report round 1, because the operator is
being told what authority the writer reached for during *this run*. The
rendered form is the distinct tool names and the total count.

Every carrier is in-memory — `LoopStepResult` and `RunResult` are not durable
state — so this costs no field and no schema bump (G2). And **the control that
proves it drives a real run that continues past the writer**; a renderer fed a
hand-built `RunResult` proves the printing, never the transport.

**And no prose matching, ever.** The fix comes from the filesystem and from the structured field. `src/agent/internal/claude-result-envelope.ts:36-41` states the reason: a sentinel phrase matched against free text will sooner or later be matched against a review that quotes the sentinel's own source file. A control in Task 2 forbids the tempting wrong fix.

### G11 — Decision 3: the identity of the AO-owned commit

Decided before implementation, and binding. Task 3 no longer decides it.

```text
AO-owned commit
  author    = AgentOrchestrator <agent-orchestrator@local.invalid>
  committer = AgentOrchestrator <agent-orchestrator@local.invalid>
  identity supplied on the individual git invocation
  no read dependency on repository or global user.name / user.email
  no git-config mutation, at any scope
```

The commit is an orchestrator effect, so its identity is the orchestrator's to
determine. Anything else makes the same run depend on whether a target
repository or a laptop happens to have `user.name` set. `local.invalid` is
`.invalid` by RFC 2606: it asserts no real person's address.

**The mechanism is `-c` on the invocation, and that is not a stylistic
preference — it is the only route this repository's seam can express:**

- `GitRunner` is `(cwd, args) => …` (`src/worktree/git-command.ts:88`). It takes
  no environment, so `GIT_AUTHOR_NAME` / `GIT_COMMITTER_NAME` cannot be reached
  without widening the seam. Widening it to pass identity would put a
  caller-controlled environment channel into the one place in the product that
  creates commits.
- The environment `runGitCommand` does supply is fixed by policy
  `capability:generic` (`src/worktree/git-command.ts:120`), whose allow-list is
  `PATH` and `PATHEXT` only (`src/auth/env-guard.ts:185,207`) — no `HOME`, no
  `USERPROFILE`. **So a commit that relied on ambient identity would already be
  standing on ground the env guard deliberately removed**, and would fail on
  exactly the machines whose identity lives only in global config. This is a
  prediction to be measured in Task 3 Step 0, not an assumption to build on.
- `-c` beats repository-local `.git/config`, which is read regardless of
  environment. That is the direction the counter-control checks: a foreign
  identity present in the target repository must not reach the AO commit.

**All three tokens are shell-inert, and this constrains the values.**
`SAFE_ARG_PATTERN` (`src/doctor/exec.ts:93`) excludes the space character, so:

```text
-c                                                ok
user.name=AgentOrchestrator                       ok   (a space would be REFUSED_UNSAFE_ARGUMENT)
user.email=agent-orchestrator@local.invalid       ok
```

A display name with a space — `Agent Orchestrator` — is **not** expressible
here and is not a value this decision may drift to. The same applies to the
commit message: `-m` takes one argument, and it too must be a single
space-free token of `[A-Za-z0-9._:@=+\/-]`. Task 3's deterministic message must
therefore be built as e.g. `AO:<taskId>:<phase>:r<round>` rather than as a
sentence. A message with spaces does not fail loudly at the seam's edge — it
returns `REFUSED_UNSAFE_ARGUMENT`, which the commit path must classify as a
refusal rather than treat as an ordinary Git failure.

### G12 — The commit *effect* is bounded, not only the commit identity

G11 fixes who the commit says it is. It does not fix what the commit contains.
`git add --all` followed by `git commit` is not the single primitive it looks
like: the **target repository** gets to run code in the middle of it.

```text
scope PASS on the measured delta
        ↓
git add --all                     ← .gitattributes clean filters may run
        ↓
git commit                        ← pre-commit, prepare-commit-msg, commit-msg run
                                    post-commit runs after
        ↓
hook edits and stages forbidden/config.ts
        ↓
HEAD moved, worktree clean, every post-commit assertion green
```

That is the same authority class G1 exists to close, re-opened *after* the last
gate. Repository-local `commit.gpgSign=true` is the milder version of the same
thing: the AO commit becomes dependent on foreign local configuration.

**Control one: a positive equality proof on the committed path set.**

```text
scope gate approves         set S of changed paths
AO commits
post-commit measurement     paths(commit) == S, as SETS
                            mismatch → refuse, park, do NOT undo
```

Read from the object itself (`diff --name-only -z <base> <commit>`), compared as
an order-independent set: sorted, de-duplicated, and in one path form on both
sides. `-z` is not optional — it removes `core.quotePath`, a target-controlled
setting, from the comparison, and Git prints POSIX-shaped paths even on Windows
(`src/worktree/worktree-registry.ts:10-34`), so the approved set must be brought
into that same shape rather than compared as raw strings.

**What this proves, stated exactly, because the first draft of G12 over-claimed
it.** It was written here that any injection "changes the committed path set and
is caught by one assertion". That is false, and the counter-example is a
mechanism this section names itself:

```text
approvedPaths = { src/work.ts }
.gitattributes: src/work.ts filter=foo     +  local config: filter.foo.clean = <command>

git add --all  → the command RUNS
               → the staged blob is not the bytes the scope gate approved
               → a sentinel outside the commit is written

paths(commit) == { src/work.ts } == approvedPaths        ← GREEN
```

So the honest scope of control one is:

```text
proves        committed path authority == approved path authority
does NOT prove   the committed bytes are the approved bytes
does NOT prove   no target-repository code executed
does NOT prove   nothing happened outside the commit object
```

It stays, because it is the only control that covers *unknown* path-adding
mechanisms. It is not the whole boundary and this plan may not call it
exhaustive.

**Control two: fail closed when Git would apply an executable driver to a path
AO is about to stage.**
Content-transforming and code-executing drivers reach AO only through
configuration — an in-tree `.gitattributes` naming `filter=foo` does nothing
unless `filter.foo.clean`/`.process` is *configured*. But the scope that
configures it is not the repository's to choose, and an earlier draft of this
section got that wrong: it argued that a missing `HOME` leaves only
`.git/config`. It does not. Git resolves **system**, global, local and
**worktree** scopes, and any of them may pull in further files through
`include` / `includeIf`. Removing `HOME` removes one scope, not the question.

```text
system scope (or any other):  filter.foo.clean = <command>
target repo .gitattributes:   src/work.ts filter=foo

a scan of --local              sees nothing
git add --all                  foo is configured as far as Git is concerned
                               → the command runs
```

So the check is not "read the local config". And it is not "refuse on any driver
key" either — **that predicate was measured and it is unusable**:

```text
git config --list --show-scope --name-only -z   on the development machine,
git 2.55.0.windows.3, in a scratch repository:

  system   filter.lfs.clean          ← Git for Windows ships Git LFS
  system   filter.lfs.smudge
  system   filter.lfs.process
  global   filter.lfs.clean   …
```

A blanket refusal would therefore refuse **every commit in every repository on
this machine**, CargoCheck included. The predicate has to be what makes a
driver dangerous *here*: that Git would apply it to a path AO is about to
stage. Git owns that question and answers it directly — so ask it rather than
inferring it from `.gitattributes` by hand.

```text
before staging, both reads through the production seam, same cwd:

1  which drivers does Git resolve at all?
     git config --list --show-scope --name-only -z
     → scope\0key\0 …            (measured; --name-only means the configured
                                  command never enters this process)

2  which of them apply to the paths being staged?
     git check-attr filter -z -- <approvedPaths>
     → path\0filter\0value\0 …   (measured; value is `unspecified` when none)

refuse when   a path in approvedPaths has an assigned filter driver
              AND that driver has .clean or .process configured in any scope
  → TARGET_CONFIG_EXECUTES_CODE { findings: [{ key, scope }] }
  → stage nothing, commit nothing
```

**Accepted consequence:** AO will not commit a path whose assigned filter
driver has an executable clean or process command configured in the effective
Git configuration — LFS-tracked files included. It parks and an operator does
it. A path whose driver is merely *named* and never defined is not refused.
That is
the honest reading of "AO does not run target-repository code inside its own
commit", and it is stated here rather than discovered when a repository with
LFS-tracked assets parks.

**Path-independent executable configuration** — `core.fsmonitor` and its
relatives — is deliberately *not* part of this refusal. It is not reachable via
`check-attr`, it already runs during today's `status`/`diff` observation, and a
blanket refusal on it would fail closed on ordinary machines for a pre-existing
exposure. It goes to the follow-up register beside Q4 and Q5, named and
measured, not silently folded in here.

Two properties of that reading are requirements, not details:

- **Same seam, same cwd, immediately before the effect.** A configuration read
  taken by a different mechanism, in a different directory, or at an earlier
  moment answers a different question than the one `git add` will ask. That is
  the capability-guard rule: a guard observed anywhere other than at the effect
  merely relocates the race.
- **Key names and scopes are evidence; values are not.** The refusal carries
  which keys were found and in which scope. It never carries the configured
  command string — that is foreign text, and this refusal is printed to an
  operator.

**Residual, stated:** a configuration change landing between AO's read and AO's
`git add` would defeat this. The window is between two consecutive Git
invocations by AO itself, with no writer running — the writer has already
returned and holds no shell. That is the bound; it is not zero, and it is
written here rather than left to be assumed.

Refusing is deliberate, and it is the right direction: AO declines to commit
into a repository that would run its own code inside AO's commit, rather than
running it and measuring afterwards. A post-hoc measurement cannot un-execute a
command or un-write a sentinel.

**Control three: hook and signing neutralisation**, as below — defence in
depth for the mechanisms that do not need a driver configured.

**Residual, named rather than implied:** with all three in place, an in-scope
file's *content* is trusted because no content-transforming driver was
configured, not because it was compared byte for byte against what the scope
gate saw. Closing that would mean pinning blob hashes at the gate and
re-checking them in the object. It is written into the follow-up register as
the exact remaining gap, with this sentence as its statement.

**Hook and signing neutralisation is the second half, defence in depth**, and
its spelling is deliberately *not* fixed here: it is measured in Task 3
Step 0b. `--no-verify` alone is not a proof — it does not cover
`prepare-commit-msg` or `post-commit` — so the candidate to beat is a
hooks-path override plus explicit signing suppression, chosen on evidence. The
override path is itself an argument and must be shell-inert
(`SAFE_ARG_PATTERN`, no spaces), which rules out anything built from a
temp directory whose name might contain one.

**Accepted consequence, stated rather than discovered:** an AO commit does not
run the target repository's hooks. A repository that formats or generates
content in `pre-commit` will see AO commits that skipped it. That is the
correct direction — a scope gate that a target repository can edit around is
not a gate — and it belongs in the module comment and in the README narrative.

**No undo.** If the committed path set does not equal the approved set, the
commit object exists and stays. AO parks at `HUMAN_DECISION_REQUIRED` with the
commit named as evidence. It does not `reset --hard`, because a rollback is an
effect too, it is the most destructive one available here, and the operator
needs the artefact in order to see what the repository did.

**And one part of this is older than this slice.** `git worktree add` performs a
checkout, and a checkout runs `post-checkout`. If that is true through this
product's seam, then AO has been running target-repository hook code since
workspace preparation existed, and the commit merely makes it *scope-relevant*
for the first time. Task 3 Step 0b measures it. It is **not** repaired here —
that would be a second authority slice, and G10 fences it out — but if measured
true it is written into the follow-up register as a named finding rather than
left as a thing this plan quietly noticed.

## The rerun gate

The second CargoCheck dogfood counts only when all of these are true:

1. The G3 vector is in production, pinned by a test, and `npm run verify:writer-authority` passes **both** stages: the writer edits inside the worktree and **cannot** commit (no shell, no MCP, escape blocked, tree left dirty), then the AO path measures the delta, enforces scope, commits, and leaves HEAD moved and the tree clean.
2. Authority is hermetic — `--setting-sources ""` and `--strict-mcp-config` — so the run proves something about the product and not about one laptop.
3. A writer pass with no measured effect cannot be a success, and `permission_denials` is reported **in the rendered operator output of a run that continued past the writer step** — distinct tool names and count, on failing and succeeding passes alike, accumulated across rounds — without being a verdict.
3b. **The AO commit is bounded on all three of G12's controls**: the committed path set equals the approved set against a hook that tries to inject; a target repository with a configured executable driver is refused *before* staging, with the driver provably never run; signing is demanded and neutralised; and the divergence case parks without an undo. The path-set check is not claimed to be more than it is.
4. `READY_FOR_PR` refuses an empty delta against freshly observed evidence, with the negative and positive controls green and the record-vs-record mutant red.
5. A tautological predecessor is refused by name, and the legal chain still starts.
6. The reviewer receives body, truncation flag and round, proven by the differential payload control; absence parks rather than degrading.
7. The remediation hand-off survives the budget boundary, with the byte-identical no-boundary variant green.
8. The no-effect controls are inverted rather than deleted, and the deliberate scope-violation and lease-loss cases stay green.
9. **G5 residual closed:** the dogfood transcript's literal refusal strings compared against the measured permission-denial prose. Match → same defect, closed. No match → a live second mechanism, and the rerun blocks again.
10. `npm run verify` passes on a clean machine, and the opt-in gate has been run at least once.
11. **Task 12 answered**, in writing, as one of its three outcomes.

Then the run can deliver what the first could not:

```text
real Claude writer actually edits
        ↓
AO commits → A produces A1, A1 != blockBase
        ↓
A SETTLED
        ↓
B.basePinnedCommit == A1
        ↓
B sees A's actual code
        ↓
both tasks complete, or stop truthfully for a genuine product reason
```

## Self-review against the decisions

- **Decision 1 (AO owns the commit)** — G1, Task 3. The writer gets no shell, no git, no MCP; the commit is AO's, under its lease, after the scope check. `writerThatCommits` is retired rather than reused, which is the consequence most easily missed.
- **Decision 2 (no schema change)** — G2. `src/core/task-state.ts` is not in the File Structure table. The two layers are Task 5 (future transitions, fresh evidence) and Task 6 (old and foreign records, truthfully named). No ledger field, no stop reason, no bump; one new member of a report-only set.
- **The commit effect, not only its identity** — G12, Task 3 Steps 0b/1/3/5. `git add --all` + `git commit` lets the *target repository* run code between the scope gate and the object, through hooks and clean filters; `commit.gpgSign` makes the commit depend on foreign local config. Three controls, each with its scope stated rather than implied: **(1)** the committed path set equals the approved set, compared as normalised sets — this proves path authority and is the only control that covers *unknown* path-adding mechanisms, but it is explicitly **not** exhaustive, since a clean filter can alter the approved file's bytes and write a sentinel outside the object while leaving the path set identical; **(2)** a pre-staging refusal, `TARGET_CONFIG_EXECUTES_CODE` carrying `{key, scope}`, when Git's *effective* configuration (all scopes, includes resolved by Git) defines an executable driver **that `check-attr` says applies to an approved path** — path-scoped because a blanket predicate was measured to refuse every commit on any machine with Git LFS — read with `--name-only` so the configured command never enters the process, and read *before* staging because a post-hoc measurement cannot un-run a command; **(3)** hook and signing neutralisation, spelled only after Step 0b measures it. Divergence parks with no undo. The residual — in-scope *content* is trusted because no transforming driver was configured, not because bytes were pinned at the gate and re-checked — is named in the register instead of being covered by a stronger word. Measured, not assumed: whether `worktree add` already runs `post-checkout`, and where a clean filter *first* executes; both may turn out to be older exposures than this slice, fenced out by G10 and recorded rather than quietly repaired.
- **Decision 3 (commit identity)** — G11, Task 3. Decided before implementation, not left to the implementer: `AgentOrchestrator <agent-orchestrator@local.invalid>`, per invocation, no config mutation. Its counter-control is a repository with no identity at all, and its opposite direction is a foreign identity that must not leak. Two seam facts constrain it and are stated where they bite: the runner takes no environment, and the argument pattern excludes the space — which is also why the commit message must be one token.

- **Commit after scope** — G1, and Task 3's third control fails if the order is reversed.
- **`permission_denials` reported, not decisive** — G6, Task 2, with mutants for both wrong directions: turning denials into a failure, and matching prose.
